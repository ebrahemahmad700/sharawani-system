01What this system is

Every official letter reaching the municipality is registered as incoming, routed through the rooms that must act on it, answered, and registered as outgoing when the case closes. Today that happens in a paper register book, and letters get lost between rooms.

This system mirrors that journey. It does not replace the paper letter. It tracks it, holds a scanned copy, records who held it and for how long, and makes any file findable again, both on screen and on the physical shelf.

Non-goal

This is not a paperless office project. Staff will keep printing, signing by hand and stamping. The system's job is to know where every letter is, and to make the archive searchable.

How it works

Sending to one room inserts one row, status active. Sending by sequence inserts every row in one transaction: the first active, the rest waiting. When a room completes its step, the next waiting row in the same group is promoted and document.current_room_id moves with it. If the last step carries return_to_assigner, one more step is appended back to the assigner.

This single table produces the trail view, every inbox query, the overdue report and the elapsed-time figures. Nothing else needs storing.

Issuing numbers

Numbers must never be composed by the browser. Two clerks registering in the same second will otherwise produce the same number.

number_counter    kind ('incoming'|'outgoing'), year, next_value
                  primary key (kind, year)

UPDATE number_counter
   SET next_value = next_value + 1
 WHERE kind = 'incoming' AND year = 2026
RETURNING next_value - 1;
Never reuse a number

Even a cancelled letter keeps its number and shows as cancelled. A gap in the register is exactly what an auditor looks for.

05Core workflows

Register incoming

  1. Letter arrives at the registry room and is scanned. The scan lands in a watched folder.
  2. Clerk opens the registration form. The next number is shown, locked.
  3. Clerk fills sender, subject, type and priority, then attaches the scan from the tray.
  4. Clerk records the shelf where the paper original goes.
  5. Save, either register only or register and send, which opens routing.

Route by sequence

  1. Sender picks a saved route, or builds one by dragging rooms into order.
  2. Each step gets its own due days.
  3. Optionally, return to me when finished.
  4. All steps created in one transaction, the first active. Each completion activates the next automatically.

A room answers

Received time is stamped on first open. There are three ways to answer, and all three are real:

  • Print, write by hand on the back, scan, attach. This is how most rooms actually work and it must be a first-class path, not an afterthought.
  • Attach a new letter, written in the system or uploaded.
  • Note only, typed into the step.

A room can also return a letter to whoever sent it with a reason. That creates a returned step, never a deletion.

Close and register outgoing

Registry sees documents whose last step is done, issues the outgoing number, picks which attachments go out, records the send channel and writes the reply summary. The case closes, the room assignment clears, and the document lives in the archive.

Deputy delegation

When a leave record becomes active for a room head, incoming steps for that room are assigned to the deputy automatically and the inbox shows who is covering. When the leave ends, assignment reverts. Without this, letters stop dead in an empty room, which is precisely how the paper system fails today.

06Kurdish text handling

Highest technical risk in the project

If search does not work, the rooms 8 and 9 requirement fails, and that requirement is the reason the project exists. Sorani in Arabic script has heavy spelling variance. Staff type on mixed keyboards, and the same word appears three ways in the same folder.

Normalisation table

Apply on write into every *_search column, and apply identically to every query string. Keep the original text untouched for display.

InputFold toCode pointReason
يیU+064A → U+06CCArabic yeh from an Arabic keyboard
كکU+0643 → U+06A9Arabic kaf
هەU+0647 → U+06D5Word-final. The single most common Sorani error
ةەU+0629 → U+06D5Arabic teh marbuta
أ إ آا→ U+0627Hamza carriers
ڕرU+0695 → U+0631People omit the ring
ڵلU+06B5 → U+0644People omit the ring
ۆوU+06C6 → U+0648Frequently confused
ێیU+06CE → U+06CCFrequently confused
٠–٩0–9U+0660–0669Arabic-Indic digits
۰–۹0–9U+06F0–06F9Extended Arabic-Indic digits
‌removedU+200C / 200D / FEFFInvisible joiners break every match
ـremovedU+0640Decorative tatweel stretching
◌َ ◌ِremovedU+064B–U+0652Harakat diacritics

Folding ڕ ڵ ۆ ێ is deliberate. It loses precision but catches how people actually type. Precision comes back by ranking exact matches higher.

Implementation

  • PostgreSQL with the pg_trgm extension, GIN trigram index on each search column.
  • Normalise the query, rank by similarity(), boost exact prefixes.
  • Plot numbers get their own exact-match path. 247/5, 247-5 and ٢٤٧/٥ must all find the same record.

Display

  • Every page is right-to-left. Latin runs, meaning filenames and usernames, must be wrapped left-to-right or they render scrambled.
  • Noto Kufi Arabic for headings, Vazirmatn for body. Both cover ڕ ڵ ۆ ێ ە. Bundle them locally; the server is on a LAN with no guaranteed internet.
  • Arabic-Indic digits in the interface, Western digits in the database.
  • Kurdish alphabetical order is not Unicode code point order. Use a Kurdish collation for name lists, or accept the difference in version one and write it down as a known limitation.

AutoCAD files

DWG cannot be displayed in a browser. It is a closed binary format. Three options, in order of cost:

  1. Store and download only. Staff open it in AutoCAD.
  2. Require a PDF alongside. The uploader attaches both. Preview shows the PDF. Ship this in version one.
  3. Server-side conversion. The free ODA File Converter handles DWG to DXF and PDF. Revisit once the archive is populated.

Scanning

This detail decides adoption

One network scanner per floor, set to scan-to-folder. The server watches those folders and new files appear in a tray, tagged with scanner and timestamp. The clerk attaches in one click, with no file browsing and no USB drives.

If registering a letter takes four minutes of walking, staff will quietly go back to paper, and no screen in the design can save it.

The system lock

The mayor asked to be able to shut the system down. What he needs is a maintenance lock, not a power off: set a flag with a message, invalidate every session but his, refuse every login but his, and write the action to the log with who, when and why. Unlocking is one click. A literal power-off leaves no audit trail and no clean way back in.

The assistant, a real bot, still free

The mayor asked for something he can talk to, not a menu of buttons. That is achievable, offline, and at no licence cost. The design that makes it both smart and trustworthy is tool calling.

How it works

The model never answers from its own knowledge. It reads the question, decides which database function to call, receives real rows back, and writes the reply from those rows only.

The model handles language. The database handles facts. That split is what makes it feel smart while making it structurally unable to invent a document number.

Guard rails

Non-negotiable, and easy to get wrong
  1. Read-only database user. The bot's connection physically cannot write.
  2. No raw SQL from the model, ever. It calls named functions with typed arguments. Nothing else reaches the database.
  3. Permission filtering lives in the function, not the prompt. Every function takes the asking user's identity and returns only rows that user may see. Never enforce this in a system prompt, because a system prompt can be talked around.
  4. Every answer cites document numbers, and those come from rows, never from the model.
  5. No rows means no answer. The bot says it found nothing. It never fills the gap.
  6. Every question and answer is written to the activity log.

The choice is not really three-way on quality

Renting Qwen does not make Qwen better at Kurdish. Quality is a property of the model, not the host. The meaningful split is Qwen-class Kurdish, which you can have free on your own hardware, against frontier Kurdish, which only comes hosted.

How to decide · measure, do not argue

This question is settled cheaply with evidence rather than opinion.

  1. Write 50 real Kurdish questions with correct answers, taken from what the mayor and room heads actually ask.
  2. Run them through each candidate: local Qwen 14B, a hosted large Qwen, and a frontier model.
  3. Have a Kurdish speaker grade the answers blind, not knowing which model produced which.
  4. Pick the cheapest one that passes.

That costs a few dollars in API calls and half a day of someone's time, and it replaces an argument with a number. Do it in phase 0, because it needs no working system, only the question list.

Option A · local open model

Free forever, works offline, nothing leaves the building. Covered in full below under the model table, the Kurdish quality techniques, and the capacity and hardware figures. The Kurdish is the weak point.

Option B · hosted open model, Qwen and similar

Renting an open model is dramatically cheaper than a frontier API, and for a municipal budget that matters. Indicative third-party pricing, which you should verify because these rates move constantly and vary by provider:

Model classIndicative in / out per 1MMonthly at our load
Qwen3 8B class~$0.04 / $0.10~$10
Qwen3 32B class~$0.10 / $0.30~$28
Qwen3 235B class~$0.35 / $0.40~$80
  1. Hosting Qwen does not improve Qwen's Kurdish. Paying for a hosted 32B buys roughly what the graphics card buys for free, minus offline operation and minus data staying in the building. The genuine reason to rent rather than buy is access to the very large models you cannot run on one consumer card. A 235B-class Qwen writes noticeably better Kurdish than 14B, and $80 a month for that is a real bargain against $430.
  2. Know which provider you are actually talking to. Aggregators route to whoever is cheapest that minute. Quantisation, latency and quality vary between them, and some log prompts for training unless you opt out. For municipal data, read the retention policy of the specific provider, not the aggregator's.
  3. Data residency. The first-party Qwen API is operated from China. For a government body that is a question to answer deliberately, exactly as the privacy section answers it for any hosted option.
  4. Small models are unreliable at tool calling. Emitting valid JSON every time is what keeps the bot working at all. 32B and above is dependable; 7 to 8B is not. Do not buy the cheapest tier for a tool-calling agent, because a broken tool call is a broken answer.
The efficient hybrid

Most questions are one lookup and one sentence, which a small model handles fine. Route only ambiguous or multi-step questions to a better model. Ninety percent cheap, ten percent good, and the mayor meets the better model precisely on the questions that need it.

Option C · hosted frontier API

What actually crosses the wire

This matters more than people assume, and the tool-calling design changes the answer. The API receives the question the user typed, and the rows a function returned: document number, subject line, room name, holder name, dates.

It never receives scanned letters, attachments, PDF contents or identity documents. The exposure is metadata, not correspondence. Subject lines do carry citizen names and plot numbers, so this is not nothing, but it is a far smaller surface than every letter leaving the country. Zero-retention arrangements are available from providers for organisations that require them.

Cost at the load in the capacity table

66,000 questions a month. Per question roughly 3,000 input tokens, of which about 2,000 is the fixed system prompt and tool schemas, and 400 output tokens. Prompt caching is the whole game: that 2,000-token prefix is byte-identical on every call, and cached it reads at about a tenth of the input price.

ModelModel IDIn / Out per 1MMonthly, cached
Claude Opus 5claude-opus-5$5 / $25~$1,080
Claude Sonnet 5claude-sonnet-5$2 / $10~$430
Claude Haiku 4.5claude-haiku-4-5$1 / $5~$240

The caching trap that would cost you silently

Minimum cacheable prefix is not smaller on cheaper models

A 2,000-token system prompt caches on Opus 5 and Sonnet 5. On Haiku 4.5 it silently does not cache at all: no error, no warning, just a bill around 40% higher than expected.

ModelMinimum prefix to cache
Claude Opus 5512 tokens
Claude Sonnet 51,024 tokens
Claude Haiku 4.54,096 tokens

The fix is a happy one. Pad the Haiku system prompt past 4,096 tokens with more hand-written Kurdish answer examples. That crosses the caching threshold and improves the Kurdish at the same time. Two problems, one edit.

Caching rules to follow

  1. Freeze the system prompt. Never interpolate today's date, the user's name or a request ID into it. Anything at the front of the prefix invalidates everything after it on every call. Put dynamic context in the messages instead.
  2. Serialise tool definitions deterministically, sorted by name. Tools render at position zero, so reordering them invalidates the whole cache.
  3. Use the five-minute cache lifetime. Office-hours traffic keeps it warm continuously, and a read refreshes the timer for free.
  4. Verify with cache_read_input_tokens. If it is zero across repeated questions, something in the prefix is changing. This failure is silent: requests still succeed, the bill is just higher.

Recommendation

Claude Sonnet 5 is the sweet spot at roughly $430 a month: excellent Kurdish, strong tool calling, and a large context window. Claude Opus 5 is the better model and the right choice where quality outweighs cost. Claude Haiku 4.5 at roughly $240 is genuinely viable here, because the database does the reasoning and the model mostly has to phrase an answer.

A routing split is the efficient middle: routine lookups to Haiku, anything ambiguous or multi-step to Sonnet. That lands near $300 a month at close to Sonnet quality.

The two real drawbacks

  • It stops when the internet stops. Rania's connection is not guaranteed, and a bot the mayor relies on that dies with the link is worse than no bot. Keep the rules-and-SQL fast path as an offline fallback so questions still get answered when the line is down.
  • It is a recurring bill. Sonnet 5 costs roughly $5,200 a year, against a one-time $1,000 to $2,500 for local hardware. The API buys quality, not savings.

Making the Kurdish good

This is where the effort actually goes. Three free techniques, and they compound.

  1. Few-shot the system prompt. Put twenty correct, hand-written Kurdish answer sentences in the prompt. Open models write far better Sorani when they have real examples to pattern-match against. Cheapest win by a wide margin.
  2. Template the skeleton, let the model fill it. Give each tool a Kurdish answer template so the model adapts rather than composing from nothing.
  3. Fine-tune later, also free. After a few months, take several hundred real question-and-answer pairs from the log, correct the Kurdish by hand, and LoRA fine-tune Qwen with Unsloth on the same graphics card. No cloud, no cost, and the biggest single quality jump available.

What that means for hardware

Three thousand questions at 400 output tokens each is 1.2 million output tokens a day. A used RTX 3090 running Qwen 14B at 4-bit, served with vLLM, produces roughly 400 to 800 tokens a second across batched users. The entire day's work is therefore thirty to fifty minutes of actual GPU time, spread across eight hours.

One card covers the whole municipality

The bot sits idle around 85% of the time even under heavy use. Adding more users barely moves the hardware requirement. What moves it is how many people press send at the same moment.

Serve with vLLM, not Ollama, above about ten users

Ollama is excellent for development and for a handful of people, but it does not batch concurrent requests well. vLLM is equally free and delivers roughly five to ten times the throughput on the same card. Develop on Ollama, deploy on vLLM.

At peak, twenty simultaneous questions on one 3090 means the last person waits eight to fifteen seconds. That is fine provided the interface shows a visible thinking state. Silence is what makes people think it is broken.

One purchase of roughly $1,000 to $2,500 buys a machine that runs both the application and the bot. After that, effectively nothing.

Set against the hosted API

The same load hosted is roughly $10 to $80 a month on a Qwen-class open model, or $240 to $1,080 on a frontier model with caching. The card is a one-time purchase; hosting is a bill every month. Note that hosted Qwen and local Qwen give you the same Kurdish, so renting the small ones buys convenience rather than quality. Renting a very large Qwen, which no single consumer card can run, does buy quality.

The fallback layer

Keep a rules-and-SQL matcher, but as a fast path and a safety net, not as the product. The handful of most common questions skip the model entirely and answer instantly. If the graphics card, the model or the server is down, the bot degrades to templated answers instead of breaking.

Effort, honestly

The tool-calling bot is roughly five to seven weeks, against two to three for rules alone, and it needs the hardware above. In exchange the mayor gets follow-up questions, vague questions, combined conditions and a genuine conversation. That is what he asked for.

What not to do, free cloud tiers

Free, but not for this

Google AI Studio, Groq and others offer generous free tiers. The reason to avoid them here is not price. Every question would send municipal correspondence to a third-party server outside Iraq. Free tiers also carry rate limits, change without notice, and can be withdrawn entirely. A system the mayor depends on should not rest on someone else's promotional pricing.

One reframe is still worth making. Much of what people expect from a bot here is really good search. The trigram search in §6 costs nothing and answers "everything about plot 247/5" better than any language model would. Build the search well first, and the bot has less work left to do.

11The digitisation track

Runs from day one, in parallel with everything

This is the long pole of the project. The archive in rooms 8 and 9 does not digitise itself. Someone has to open every folder, scan or photograph every drawing, and type in the plot number, neighbourhood and shelf position.

Throughput

Work the real figure once Q6 is answered. The shape of the calculation:

files ÷ (files per person-hour × hours per day × people) = working days

Large-format drawings are slow. A realistic rate is 15 to 30 files per person-hour including indexing, and lower for fragile old paper. A ten-thousand-file archive with two people working full time is measured in months, not weeks.

What is needed

  • A large-format scanner, or a copy stand with a good camera for oversized sheets
  • Two to three dedicated staff, not people doing this when they happen to be free
  • A frozen naming convention agreed before the first file is scanned
  • A daily target and a visible progress board
  • Quality control: a second person verifies a sample of every day's work
  • Start with the plots most often requested, not with folder 1. Value arrives sooner

Naming convention

Agree this in week one and never change it.

<plot>_<neighbourhood>_<type>_<year>.<ext>

247-5_sarchnar_tanzimi_2019.dwg

The filename is a convenience and the database record is the truth. But a consistent filename makes recovery possible if the database is ever lost.

12Rollout

  1. Pilot three rooms for four weeks: the registry, legal, and one busy room. Small enough to fix problems, real enough to prove the flow.
  2. Run in parallel with paper. Every letter is registered in both the book and the system. This is deliberately doubled work and it must be time-boxed to four weeks, or people will never let go of the book.
  3. Compare the two registers weekly. Any divergence is a bug or a training gap.
  4. Cut over only when a full week shows no divergence.
  5. Expand room by room, never all at once. Each room gets a one-hour session and a printed one-page guide in Kurdish.

Training

  • Registry clerks need the most: two half-day sessions.
  • Room heads need thirty minutes. Open, print, reply, forward.
  • The mayor needs fifteen minutes and a printed card.
  • Record short screen videos in Kurdish. People rewatch those. They do not reread manuals.

14Things that will surprise you

  • WhatsApp cannot send arbitrary files without a Meta business account, a verified number and pre-approved message templates. Version one should open WhatsApp with the recipient and text prefilled and let the staff member attach the file. Full API integration is a phase 4 decision, not an assumption.
  • Email from an on-premises server often lands in spam. Send through the municipality's existing mail provider over SMTP rather than directly from the box.
  • Numbers must never be reused, even for cancelled letters. Auditors look for gaps.
  • Old drawings are physically fragile. Budget for handling care, not just scanning speed.
  • The register book may be a legal record. Confirm with the legal room whether the paper book must continue in parallel permanently. This changes the rollout plan.

15Definition of done

  • A letter can be traced from arrival to closing without opening the paper book
  • The mayor can see which rooms are overdue in one screen, without scrolling
  • A drawing can be found by plot number and the result names its shelf and folder
  • A room head on leave has their letters received by their deputy automatically
  • The six most-used forms print correctly from the system
  • A restore from backup has been performed in front of municipality IT staff
  • Two municipality staff can create users, reset passwords and take a backup unaided
  • Administrator and user documentation exists in Kurdish
  • Four consecutive weeks with no divergence between the system and any paper record still kept
